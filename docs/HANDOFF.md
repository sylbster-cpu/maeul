## 1. 최종적으로 만들고 싶은 게임

**동물의 숲의 편안한 생활, 마비노기의 다양한 생활 스킬·성장·모험, Meadgard의 아기자기한 쿼터뷰 표현과 협동 플레이를 참고한 소규모 생활형 협동 RPG.** 특정 참고작의 복제는 목표가 아니다.

- 플레이어는 **자기 집을 갖고, 키우고, 겉모습을 고르고, 안을 꾸민다.** 짓는 방식은 동물의 숲과 같다. 벽과 바닥을 하나씩 놓아 구조를 만드는 방식이 아니다(2장의 바로잡음 참고).
- 채집, 제작, 음악 연주, 사냥, 낚시·요리·농사 등의 스킬을 장기적으로 고려한다. **각 활동은 건축의 재료 공급원에 종속되지 않고 그 자체로 재미있어야 한다.**
- 혼자서도 충분히 즐길 수 있으며, 친구와 함께하면 새로운 상호작용과 협동이 발생한다. 협동은 싱글의 필수 진행을 막지 않아야 한다.
- **개인 집터 + 공동 마을/광장**이 공존하며, 친구가 남긴 결과물이 오래 유지되는 세계를 지향한다.
- 친구들의 접속 시간이 자주 겹치지 않을 것으로 예상하므로 **비동기 협동이 유용**하다. 다만 **실시간 온라인 협동은 장기적으로 반드시 구현할 기능**이며, 최대 **4인**을 지향한다.
- 실시간 멀티플레이는 초기에 생략 가능하나, 나중에 추가할 수 있도록 기본 상태·명령 구조를 고려한다. 채팅·말풍선도 장기 목표다.
- 처음부터 거대한 오픈월드가 아니라 **작은 마을을 거점으로 새로운 지역을 확장하는 세미 오픈월드**를 현실적인 방향으로 본다.
- 개발자는 AI 기반 취미 개발 초보자다. 구현 가능성, AI를 번갈아 쓰는 작업 흐름, 유지보수, 무료 또는 낮은 운영비가 중요하다.

### 바로잡음: "직접 짓는다"의 뜻 (2026-11-18)

이전 문서들은 사용자의 "직접 짓고 싶다"를 **벽과 바닥을 하나씩 놓아 건물 구조를 만드는 것**으로 적었다. GPT와 Claude 모두 그렇게 이해했고, 3차·4차 의견서와 첫 Three.js 시제품, Godot 시제품이 그 전제로 만들어졌다. **이 이해는 틀렸다.** 사용자가 뜻한 것은 동물의 숲처럼 집을 세우고 키우고 꾸미는 것이다.

사용자가 직접 고른 두 가지:

- **집 안:** 문으로 들어가면 방 화면으로 바뀐다. 걸어 들어가면 지붕이 열리는 방식은 쓰지 않는다.
- **집 모양:** 정해진 집을 고르고 키운다. 벽을 직접 긋는 기능은 뺀다.

이전 의견서들(3차·4차 회신 등)에서 벽 긋기, 자동 지붕, 실내 가림, 초안과 마감을 다룬 부분은 이 바로잡음보다 앞선 내용이므로 따르지 않는다.

## 3. 장기 기획과 초기 실험의 구분

### 장기 방향

1. 캐릭터로 자유롭게 돌아다니며 생활하고 탐험한다.
2. 건축 및 인테리어, 채집 및 제작, 음악, 사냥이 각각 독립적인 활동의 재미를 제공한다.
3. 활동은 서로 연결될 수 있지만 어느 하나가 다른 활동의 필수 종착점이 되지 않는다.
4. 공동 마을과 아이템에 플레이어의 창작 및 협력의 흔적이 남는다.
5. 비동기 공동 작업을 기반으로 **4인 실시간 협동**을 확장한다.

### 실험에서 검증할 아이디어 — 아직 확정하지 말 것

- **재료로 여는 선택지:** 바닥재, 벽지, 지붕 색, 가구, 집 키우기를 채집한 재료나 제작으로 얻게 하는 방식. 지금 시제품에서는 모두 처음부터 무료로 고를 수 있다. (이전의 "자유 건축 후 마감" 아이디어는 벽 긋기를 전제로 했으므로 이 형태로 바꿔 둔다.)
- **공동 청사진:** 서로 다른 시간에 접속해 공동 건축물에 기여하는 방식. 단순 재료 납품으로 전락하지 않도록 주의.
- **재료 속성:** 색상, 무늬 등 재료 성질을 완성품에 반영. 선택의 재미보다 인벤토리 부담이 커질 수 있으므로 소규모 검증.
- **제작물의 내력:** 만든 사람, 핵심 재료 등을 남겨 다른 플레이어 활동과 연결.
- **행동 결합:** 서로 다른 플레이어 행동이 겹치면 다른 결과가 발생. 실험 대상이지 필수 확정 규칙이 아님.
- **스킬 성장:** 숙련과 발견의 병행 가능성. 작업 횟수만 늘리는 반복 노가다와, 자유 건축을 레벨로 제한하는 방식은 지양.

## 4. Claude와 GPT의 현재 역할 및 진행 상황

- **엔진이 Three.js로 정해졌으므로 Claude와 GPT 모두 같은 Three.js 프로젝트를 수정한다.** 임시 분업(Claude는 Three.js, GPT는 Godot)은 끝났다.
- **Claude:** Three.js 시제품을 만들었고 계속 수정 중이다.
- **GPT:** Godot 4 비교 시제품을 만들었다. Godot판은 더 발전시키지 않고 기록으로 보관한다. 앞으로는 Three.js 프로젝트를 받아 이어서 수정할 수 있다.
- **사용자:** 휴대폰에서 실행 주소를 열어 직접 해 보고, 막히는 곳과 다시 꾸미고 싶은지를 알려 준다.

### Three.js 시제품의 현재 상태 (Claude 작성, 이 프로젝트가 앞으로의 기준)

- **저장소:** https://github.com/sylbster-cpu/maeul (2026-11-19 사용자가 만들고 Claude가 첫 판을 올림)
- **GitHub Pages 주소:** https://sylbster-cpu.github.io/maeul/ (`main` 브랜치가 올라간다). 사용자가 휴대폰에서 이 주소로 연 화면을 보내 주어 열리는 것이 확인됐다(2026-11-20)
- **Claude 게시 주소:** https://claude.ai/artifact/YNBUXfH2Fq92n6ARn4vNSx
  - 공유 설정은 "링크가 있는 누구나"이다.
  - 처음에는 비공개 상태라 친구에게 "페이지를 찾을 수 없음"이 떴고, 공유 설정을 바꿔 해결했다. 친구 쪽에서 다시 열어 본 결과는 기록이 없다.
- **사용자 확인:** 벽 긋기 판은 사용자가 실행해 보고 모두 정상 작동한다고 확인했다(2026-11-18). **동물의 숲 방식 판은 사용자가 열어 보고 뜻한 방식이 맞다고 확인했다(2026-11-18).** **사용자가 휴대폰에서 해 보고 문제가 없다고 답했다(2026-11-20).** 다시 꾸미고 싶은지, 친구에게 보여 주고 싶은지에 대한 답은 아직 받지 못했다. **온라인 방명록은 사용자가 실제 휴대폰에서 확인했다(2026-11-20 저녁).** GitHub Pages 주소에서 온라인 창이 열리고, 게시한 집에 서로 다른 방문자가 남긴 인사 2개가 집주인의 방명록 보기에 시각과 함께 나왔다(화면 갈무리). 게시, 방문 링크 열기, 인사 남기기, 방명록 읽기가 실제 서버에서 된다는 뜻이다. 이어서 사용자가 인사 3개 가운데 1개를 지우고 공개 중지를 눌렀다. 그 뒤 방명록 보기에 0개가 나온 화면이 있었으나 **결함이 아니었다.** 사용자가 보낸 Firebase 콘솔 화면에 집 문서가 둘 있다. 하나는 공개가 중지됐고 `notes`가 남아 있으며, 다른 하나는 공개 중이고 `notes`가 없다. 0개 화면은 둘째 집을 가진 다른 브라우저(다른 익명 계정)에서 연 것이다. 인사는 서버에 그대로 있고, 공개 중지한 집은 방문자에게 열리지 않는 것을 REST로 확인했다. **삭제와 공개 중지는 이로써 확인됐다.** 온라인 창에 지금 공개 중인지와 이 브라우저가 어느 집의 주인인지 알려 주는 표시가 없어서 생긴 혼동이다. 그래서 집주인의 온라인 창에 게시 상태 줄을 넣었다(공개 중, 공개 중지, 이 브라우저로 게시한 집 없음). 실제 휴대폰에서의 확인은 아직 없다. 같은 날 **친구가 마당에 스툴을 여러 개 늘어놓아 글자 모양을 만든 화면**을 사용자가 전해 왔다. 친구가 이 시제품으로 무언가를 만들어 보여 준 첫 기록이다.
- **실행 방법 (AI의 확인용):** 저장소에서 `npm install` → `npm run serve` → `http://localhost:5173`. 사용자는 이 과정을 할 수 없으므로 사용자 확인은 위의 두 주소로 한다. 예전에 쓰던 압축 파일 전달은 저장소가 생긴 뒤로 쓰지 않는다.
- **기술:** three.js 0.170.0을 jsDelivr CDN에서 불러온다. 빌드 도구 없는 순수 JavaScript 모듈이며, 소스는 약 2,300줄이다.
- **구현된 것 (동물의 숲 방식, 2026-11-18에 다시 짬)**
  - **두 곳:** 마당과 방이다. 마당에는 집의 겉모습이 서 있고, 집을 누르거나 문으로 걸어가면 방 화면으로 바뀐다. 방에서는 현관 깔개를 누르거나 그쪽으로 걸어 나가면 마당으로 돌아온다. 화면 위의 `집 안으로`/`밖으로` 버튼으로도 오간다.
  - **집 키우기:** 세 단계다. 방은 6×6칸 → 8×8칸 → 10×10칸으로 넓어지고 겉모습도 함께 커진다. 가구는 제자리에 남는다. 지금은 비용 없이 바로 커진다. 집이 커질 자리(마당)에 물건이 있으면 키우지 않고 이유를 알려 준다.
  - **겉모습 고르기:** 지붕 4색, 외벽 5색, 문 4색. 집은 박공지붕과 창문, 굴뚝(2단계부터)을 코드로 그린다.
  - **방 꾸미기:** 바닥재 5종, 벽지 5종을 방 전체에 한 번에 바꾼다.
  - **가구:** 15종(의자, 스툴, 탁자, 작은 탁자, 낮은 탁자, 침대, 큰 침대, 소파, 안락의자, 수납장, 서랍장, 스탠드, 화분, 러그 2종). 방과 마당 모두에 놓는다. 한 칸은 의자 하나 크기다(이전 판의 절반). 놓기, 돌리기, 집어서 옮기기, 치우기를 지원하고 겹침을 판정한다. 러그는 가구 아래에 깔린다. 현관 깔개와 집 앞에는 놓을 수 없다.

## 5. 엔진 결정의 기록

**2026-11-18, 사용자가 Three.js로 정했다.** 이유는 사용자가 컴퓨터를 쓸 수 없는 상황이어서, 휴대폰 브라우저에서 바로 확인할 수 있는 쪽이 필요했기 때문이다. Godot는 에디터와 실행 모두 PC가 필요하다.

이 결정에 대해 다음 담당 AI가 알아야 할 것:

- **계획했던 비교 시험은 하지 않았다.** 공통 플레이 시험, 수정 시험 A·B·C, 교차 인수 시험 모두 수행 전이다. 그래서 "Three.js가 Godot보다 낫다"는 근거는 없다. 근거는 "지금 사용자가 쓸 수 있는 것은 Three.js뿐"이다.
- **Godot의 장점은 검증되지 않은 채 남았다.** 시각 에디터, 모델 가져오기와 손질, 캐릭터 애니메이션, 전투 쪽 내장 기능이 그렇다.
- **Three.js 쪽에서 감수하는 것:** 시각 에디터가 없다. 모델은 묶기 도구를 거친다(`.glb` 미지원). 캐릭터 애니메이션, 길 찾기, 충돌을 직접 만든다. 사냥을 넣을 때 이 비용이 커진다.
- **나중에 엔진을 바꾸는 비용은 기능이 늘수록 커진다.** 규칙 코드(`state.js`, `history.js`, `save.js`)는 화면과 분리되어 있어 설계는 옮길 수 있지만 코드는 다시 써야 한다.
- 사용자가 컴퓨터를 다시 쓸 수 있게 되어도 이 결정을 자동으로 뒤집지 말 것. 다시 검토하려면 사용자가 먼저 요청해야 한다.

`수정시험_자료.zip`의 과제들은 비교용으로는 쓰이지 않는다. 스툴은 가구로, 벽 색 바꾸기는 벽지 고르기로, 벽에 거는 액자는 벽걸이로 모두 들어갔다.

수정 기록은 `docs/WORKLOG.md`로 옮겼다.

## 6. 두 AI의 공동 개발 운영 방안

이 저장소가 작업의 기준이다. 작업 규칙은 저장소 맨 위의 `AGENTS.md`에 있고, Claude는 `CLAUDE.md`를 통해 같은 규칙을 읽는다. 요점만 적는다.

1. 코드는 한 번에 한 AI만 고친다. 각자 `claude/…`, `gpt/…` 브랜치에서 고치고 풀 리퀘스트를 연다. 병합은 사용자가 하거나, 사용자가 시킨 AI가 한다.
2. `main`이 GitHub Pages로 올라간다. 병합한 뒤 휴대폰에서 열어 보고, 문제가 있으면 어느 AI에게든 되돌리게 한다.
3. 작업마다 `docs/WORKLOG.md`에 요청, 바뀐 파일, 돌린 시험, 확인하지 못한 것을 남긴다.
4. 이전 대화의 기억을 믿지 않는다. 저장소의 최신 소스와 기록을 읽고 시작한다.
5. 사용자가 PC를 쓸 수 없는 동안에는 사용자가 손으로 파일을 올리는 절차를 만들지 않는다.
6. Godot판의 코드는 합치지 않는다.

4. 생활 활동(채집, 제작, 음악, 사냥)은 집 꾸미기의 종속 콘텐츠가 아니라 각각 독립적인 재미를 검증한다. 실시간 4인 협동은 장기 필수 목표이며 이번 방명록 시험과 구분한다.

- 프로젝트를 생활형 협동 RPG가 아닌 **건축 전용 게임으로 좁혀 버리지 말 것**.
- 지금은 **건축 시제품의 작동·수정 가능성·배포 가능성 검증**이 목표임을 유지할 것.
- 사용자에게 이미 답한 질문(실시간 협동: 장기 필수/초기 유보, 건축+인테리어 모두 중요, 개인 집터+공동 마을)은 다시 묻지 말 것.
- 사용자 요구는 단계적으로 구현하되, 테스트하지 않은 기능을 정상이라고 확언하지 말 것.
- 같은 파일을 수정하는 요청이면 불필요한 변형본을 여러 개 만들지 말 것.
- **짓는 방식은 동물의 숲 방식이다. 벽과 바닥을 하나씩 놓는 건축으로 되돌리지 말 것.** 사용자의 말을 넓게 해석해 기능을 키우기 전에, 참고작의 어느 부분을 뜻하는지 짧게 확인할 것.
- 엔진은 Three.js로 정해졌다. 다시 논쟁하지 말 것. 다만 5장에 적은 대로 이 결정은 비교 시험의 결과가 아니라는 점을 기억할 것.
- 사용자는 휴대폰만 쓴다. **기능을 넣을 때마다 터치로 되는지 확인하고, 키보드로만 되는 기능을 만들지 말 것.** 사용자에게 PC 작업을 시키지 말 것.
