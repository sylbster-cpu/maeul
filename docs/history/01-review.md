## 총평

방향은 성립합니다. 다만 현재 인계문은 생활형 MMO 장르 전체의 기능 목록에 가깝고, 이 게임만의 규칙이 아직 없습니다. 범위도 초보 1인 개발 기준으로 몇 배 초과입니다. 인계문이 스스로 짚은 위험(범위 과다, 실시간 데이터와 저장 데이터의 분리, 호스트 부재 문제)은 정확합니다.

권고는 세 가지입니다.

- 첫 공개판의 스킬을 8개에서 3개(채집, 제작, 음악)로 줄입니다.
- 전투는 첫 공개판에서 뺍니다.
- 엔진은 Godot로 옮기지 말고 웹을 유지합니다.

## ① 기획 평가

참고작의 재미는 이 프로젝트가 가져올 수 없는 것에 기대고 있습니다. 동물의 숲은 수백 종의 수작업 콘텐츠에, 마비노기는 수많은 낯선 사람이 만드는 경제와 사회에 기댑니다. 2~4인 친구 게임에 콘텐츠 수십 종이면 두 기둥이 모두 빠집니다. 남는 것은 채집, 제작, 숙련 루프인데 이것만으로는 한두 시간 뒤에 할 일이 없어집니다.

인계문 안에 서로 충돌하는 지점이 다섯 군데 있습니다.

1. **자유 성장과 스킬 연결.** 누구나 모든 스킬을 배울 수 있고 특정 스킬 보유자 없이도 진행된다면, 6장의 예시(한 명은 목재, 한 명은 악기, 한 명은 연주)는 저절로 일어나지 않습니다. 각자 혼자 다 하는 편이 편하기 때문입니다. 분업을 만드는 압력을 규칙으로 따로 설계해야 합니다.
2. **반복 작업 지양과 숙련도.** 숙련도 수치는 그 자체가 반복 작업 장치입니다. 새로운 행동이 열리는 성장을 원한다면 해금 조건을 발견으로 두기를 권합니다.
3. **오픈월드와 작지만 깊은 게임.** 마을 하나와 숲 하나는 오픈월드가 아닙니다. 거점과 구역 구조로 부르면 불필요한 기술 요구도 함께 사라집니다.
4. **전투와 음악의 순위.** 5장은 사냥을 가장 크게 확장할 콘텐츠로 둡니다. 전투는 구현 비용이 가장 크고(동작, 타격감, AI, 지연 보정) 차별화 효과는 가장 작습니다. 음악은 후순위로 밀려 있지만, 이 목록에서 다른 게임이 잘 다루지 못하는 유일한 항목입니다.
5. **협동 예시의 비용.** 합주, 공동 건축, 축제, 협동 퍼즐은 각각 별도 시스템입니다. 협동의 재미는 모든 활동에 공통으로 적용되는 규칙 하나에서 나와야 1인 개발로 감당됩니다.

Meadgard는 검색으로 확인했습니다. 1~4인 협동 바이킹 여관 게임이고, 낮에 섬에서 사냥과 채집을 하고 밤에 여관을 운영하며, 2026년 11월 5일 얼리 액세스로 나왔습니다. 한 리뷰는 두 명이 붙으면 작업대가 빨라지는 방식이라고 썼고, 다른 리뷰는 데모가 2인에게도 벅차 솔로를 권하기 어렵다고 썼습니다. 인계문이 피하려는 두 문제가 참고작에서 지적된 셈이니, 그래픽과 낮밤 구조만 참고하는 편이 안전합니다.

## ② 개발 현실성

완성 가능한 범위는 스킬 3개, 구역 2개, 아이템 30~40종, 2~4인 접속, 저장되는 공동 마을 정도로 봅니다. 이것은 검토자의 추정입니다. 던전과 보스, NPC 기억, 나머지 스킬은 이 범위를 완성한 뒤의 일입니다.

위험한 순서대로 적습니다.

1. **멀티플레이 판정과 저장의 정합성.** 누가 판정하는지 정하지 않고 기능을 늘리면 아이템 복제, 서로 다른 화면, 저장 손상이 생깁니다. 혼자 테스트할 때는 통과하고 두 사람이 같은 나무를 동시에 벨 때 깨지는 종류라서 초보자가 고치기 가장 어렵습니다.
2. **3D 에셋과 동작.** AI는 코드는 써 주지만 화풍이 일관된 모델과 동작은 만들어 주지 못합니다. 스킬을 하나 추가할 때마다 동작이 필요합니다.
3. **이해 범위를 넘는 코드.** AI 코딩 프로젝트는 개발자가 구조를 설명하지 못하게 되는 시점에 멈춥니다. 규칙 코드를 화면 코드와 분리하고 자동 테스트를 붙이는 것이 대책입니다.
4. **저장 형식 변경.** 친구들이 가꾼 마을이 업데이트 한 번에 사라지면 회복이 어렵습니다. 저장 데이터에 버전 번호와 변환 코드를 처음부터 넣어야 합니다.

## ③ 핵심 시스템 설계

네 가지 규칙을 제안합니다.

**규칙 1. 재료의 성질이 완성품으로 이어집니다.**
재료마다 성질을 2~3개 갖고(예: 울림, 단단함, 향), 제작할 때 일부가 완성품에 넘어가 기능을 정합니다. 울림이 큰 목재로 만든 피리는 소리가 멀리 가고, 단단한 목재로 만든 도끼는 큰 나무를 벱니다. 같은 나무라도 장소, 날씨, 시간에 따라 성질이 달라집니다. 재료 10종으로도 조합의 깊이가 생깁니다.

스킬별 성장은 이렇게 나뉩니다.

- 채집: 성질을 알아보는 눈이 열립니다.
- 제작: 넘겨받는 성질의 수와 조합 방식이 늘어납니다.
- 음악: 연주가 세계에 미치는 작용의 종류가 늘어납니다.

새 성질이나 새 조합을 처음 발견할 때 해금됩니다.

**규칙 2. 한 사람은 한 번에 한 가지만 하고, 두 행동이 겹치면 결과가 달라집니다.**
연주가 들리는 동안 벤 나무는 울림이 높아지고, 등불을 비추는 동안 캔 광석에서는 숨은 광맥이 드러나는 식입니다. 혼자서는 두 번째 행동을 미리 만든 장치(연주를 녹음한 오르골, 등불 받침대)로 대신합니다. 장치는 위치와 내용이 고정이라 계획이 필요합니다. 친구는 따라다니며 상황에 맞춰 바꿔 줍니다. 같은 콘텐츠에서 솔로는 준비와 계획의 재미를, 협동은 즉흥과 호흡의 재미를 얻습니다. 솔로로 못 얻는 결과물이 없으므로 원칙 A와 B를 함께 만족합니다.

**규칙 3. 스킬은 무제한이고, 한 번 나갈 때 들고 가는 도구는 제한합니다.**
숲에 갈 때 도구 칸을 2개로 둡니다. 혼자면 목적 하나를 정해 다녀옵니다. 넷이면 도끼, 곡괭이, 악기, 등불이 한 번에 갖춰져 우연히 만난 기회에 대응할 수 있습니다. 직업을 고정하지 않고도 분업의 압력이 생깁니다.

**규칙 4. 물건에 만든 사람과 재료의 내력이 남습니다.**
공동 창고와 결합하면, 친구가 두고 간 목재로 내가 악기를 만들고 친구가 다음 날 그것을 연주하는 연결이 동시 접속 없이 성립합니다.

**음악.** 합주가 어렵다는 판단은 건반을 실시간으로 누르는 방식에만 해당합니다. 악보를 데이터로 두고 시작 시각만 맞춰 각자 기기에서 재생하면 지연 문제가 없습니다. 웹 오디오로 소리를 합성하면 음원 파일도 필요 없습니다.

**사냥.** 넣는다면 체력을 깎는 전투 대신 규칙 2의 연장을 권합니다. 동물마다 반응하는 소리, 먹이, 빛을 관찰해 유인하고 포획하는 방식입니다. 몬스터 헌터식 관찰 요소를 전투 동작과 판정 동기화 없이 얻습니다.

## ④ 기술과 구조

### 엔진

| 기준 | 웹 (TypeScript + Three.js) | Godot 4 |
|---|---|---|
| 친구 참여 | 링크 클릭 | 빌드 배포. 웹 내보내기는 ENet을 못 쓰고 WebSocket과 WebRTC로 제한 |
| AI 코딩 | AI가 브라우저를 직접 띄워 결과 확인 가능 | 에디터에서 손으로 하는 작업은 AI가 대신하지 못함 |
| 서버 | 클라이언트와 같은 언어로 무료 서버리스에 배치 | 전용 서버는 Godot를 상시 구동할 기계 필요 |
| 인벤토리, 제작, 채팅 화면 | HTML과 CSS | 엔진 UI 체계를 새로 학습 |
| 3D 기능 | 동작 전환, 충돌, 길찾기를 직접 구성 | 내장 |
| 맵 제작 | 시각 에디터 없음 | 시각 에디터 있음 |

웹을 권합니다. 이 게임은 화면의 절반이 UI이고, 친구가 링크로 들어오는 것이 중요하고, 호스트 없이 유지되는 마을이 필요합니다. 세 조건 모두 웹이 유리합니다. Godot가 더 나은 조건은 액션 전투 중심, 설치형 전용, 물리 중심인데 제안한 구조는 여기에 해당하지 않습니다. 배제하지 못한 위험은 표의 아래쪽 두 행입니다. 다음 방법으로 줄일 수는 있어도 없어지지는 않습니다.

### 표현 방식

규칙은 2D 격자로, 화면은 3D로 만들기를 권합니다. 충돌, 길찾기, 건축 배치, 저장, 동기화가 모두 2차원 배열 문제로 단순해집니다. 카메라는 고정하고 무료 로우폴리 에셋 팩을 씁니다. 처음 두 단계는 상자와 캡슐만으로 진행합니다.

3D 쿼터뷰에서 개인이 겪는 어려움은 대략 이 순서입니다.

- 에셋과 동작의 일관성
- 건물과 나무에 캐릭터가 가려지는 문제
- 클릭 대상 판정
- 에디터 없는 맵 배치
- 노트북 성능

### 멀티플레이

| 구조 | 무료 조건 | 호스트 없이 접속 | 문제 |
|---|---|---|---|
| P2P, 한 명이 호스트 | 무료 | 불가 | 일부 네트워크에서 연결 실패, 저장이 호스트 PC에만 남음 |
| Firebase 실시간 DB | 동시 100접속, 월 10GB 전송 | 가능 | 위치 동기화가 전송량을 소모, 판정 코드를 둘 곳이 없음 |
| Supabase | 무료 | 가능 | 1주 미사용 시 프로젝트 일시정지 |
| Cloudflare Durable Objects 방 서버 | 하루 요청 10만 건, 저장 5GB | 가능 | 서버 코드를 직접 작성, 한도 초과 시 그날은 중단 |

방 하나를 Durable Object 하나로 두는 구조를 권합니다. 수신 메시지는 20개가 요청 1건으로 계산됩니다. 4인이 초당 10회 위치를 보내면 시간당 약 7,200건이고, 하루 13시간쯤 쓸 수 있습니다. Supabase의 일시정지는 가끔 모이는 취미 게임에 맞지 않습니다.

데이터는 인계문 6장의 구분대로 나누되 처리 방식을 다르게 둡니다.

- **위치와 동작**: 초당 10회 중계하고 저장하지 않습니다. 받는 쪽에서 보간합니다.
- **인벤토리와 세계 변경**: 명령으로 서버에 보내고, 서버가 도착 순서대로 적용한 뒤 모두에게 알립니다. 같은 나무를 동시에 베면 한 명만 성공합니다.
- **공동 마을**: 방 저장소에 버전 번호와 함께 기록합니다. 아무도 없으면 세계는 멈춥니다.
- **채팅**: 중계만 합니다. 길이와 횟수 제한은 서버에서 겁니다. 채팅 문자열을 HTML로 삽입하지 않아야 하고, 방 코드는 추측하기 어려운 길이로 둡니다.

야생 동물 이동 같은 일시적 연산은 먼저 들어온 사람의 브라우저가 맡고, 그 사람이 나가면 다음 사람이 넘겨받습니다. 친구끼리라 부정행위 방지는 필요 없습니다.

### 초기에 만들 공통 기반

1. 아이템, 성질, 제작법, 구역을 코드 밖 데이터 파일로 두고 고정 ID를 붙입니다.
2. 모든 상태 변경을 명령, 검증, 적용, 이벤트 순서로 통과시킵니다. 싱글은 로컬에서 적용하고 멀티는 서버를 거칩니다. 멀티플레이를 나중에 억지로 붙이지 않는다는 말의 실체가 이것입니다.
3. 세계 상태를 통째로 직렬화할 수 있게 하고 저장 버전과 변환 코드를 둡니다.
4. 규칙 코드를 화면과 분리하고 자동 테스트를 붙입니다.
5. 격자 좌표와 개체 고유 ID를 정합니다.
6. 시간과 날씨를 한 곳에서 관리합니다.

## ⑤ 로드맵

| 단계 | 만드는 것 | 검증할 것 |
|---|---|---|
| 0 | 두 브라우저에 상자 둘이 보이고, 놓은 물건이 새로고침 뒤에도 남는 판을 무료 서버에 배포 | 가장 위험한 기술이 실제로 동작하는가 |
| 1 | 혼자 하는 회색 상자 판. 격자 맵, 성질 있는 재료 2~3종, 제작 5종, 로컬 저장 | 어떤 재료를 어디서 캘지 고르는 일이 10분간 재미있는가 |
| 2 | 2인 접속, 공동 창고, 채팅 | 동시 채집 충돌, 재접속, 퇴장 후 저장. 친구가 두고 간 물건을 발견하는 경험이 작동하는가 |
| 3 | 악보 연주, 겹침 규칙, 오르골 장치 | 혼자 할 때와 둘이 할 때 플레이가 실제로 달라지는가 |
| 4 | 3D 에셋 적용, 가구 배치, 숲 구역 | 가림 처리, 성능, 꾸민 결과가 남는 만족감 |
| 5 | 도구 칸 제한, 4인, 유인 포획 동물 1종, 2~3시간 분량 | 친구들이 시키지 않아도 다시 접속하는가 |

1단계에서 재미가 없으면 그래픽과 콘텐츠를 더해도 나아지지 않으므로 거기서 규칙을 고칩니다. 3단계에 이 게임의 성패가 걸려 있습니다. 각 단계는 링크로 열리는 플레이 가능한 판으로 끝냅니다. 주 5~10시간 기준으로 0~2단계에 2~3개월, 5단계까지 6~9개월로 추정하지만 근거가 약한 숫자입니다.

## ⑥ 대안과 미결정 사항

가장 큰 대안은 비동기 협동을 기본으로 삼는 것입니다. 성인 친구들의 접속 시간은 잘 겹치지 않습니다. 공동 마을에 흔적을 남기는 협동을 바탕에 두고 실시간 접속을 그 위에 얹으면, 아무도 함께 접속하지 않은 날에도 게임이 유지됩니다. 실시간이 꼭 필요한 것은 합주와 겹침 규칙뿐입니다.

인계문 10장 항목별 의견입니다.

1. **표현 방식**: 규칙은 2D 격자, 화면은 3D 로우폴리, 초기에는 회색 상자.
2. **엔진**: 웹.
3. **전투**: 첫 공개판까지 제외하고 유인과 포획으로 대체.
4. **성장 구조**: 발견으로 해금.
5. **서버**: 방 서버가 중계와 저장을 담당.
6. **호스트 없는 공동 마을**: 필요합니다. 권장 구조에서는 추가 비용이 없습니다.
7. **거래와 경제**: 제외. 2~4인으로는 시장이 성립하지 않고 공동 창고와 선물로 충분합니다.
8. **맵**: 손으로 만든 고정 맵. 절차적 생성은 자원 위치와 성질 배정에만 씁니다.
9. **플랫폼**: PC 우선. 터치 조작은 지금 설계하지 않습니다.

NPC가 기억하고 반응하는 기능은 대사 분량 비용이 커서 첫 공개판 이후로 미루기를 권합니다.

## 반론을 받아 볼 지점

이 의견서에서 검토자의 판단이 틀렸을 가능성이 큰 곳입니다.

1. **웹 유지 권고.** 3D 동작 전환과 맵 제작 도구를 직접 만드는 부담을 과소평가했을 수 있습니다.
2. **전투 제외.** 개발자가 사냥에 두는 기대가 크다면 유인과 포획이 그 자리를 채우지 못할 수 있습니다.
3. **겹침 규칙의 재미.** 문서 검토로는 결론이 나지 않습니다. 로드맵 1~3단계 시제품으로만 확인됩니다.

## 확인하지 못한 부분

- Meadgard 내용은 검색 요약과 리뷰 기사에 근거합니다. Steam 스토어 원문을 직접 열지 못했고, 플레이해 본 정보도 아닙니다.

- AI가 GDScript에서 Godot 3과 4 문법을 자주 혼동한다는 점도 웹을 권한 이유 중 하나인데, 측정 자료가 없는 경험적 판단입니다.
- 완성 가능 범위와 개발 기간은 추정입니다.
