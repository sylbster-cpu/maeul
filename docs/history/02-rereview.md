## 2. 질문 1. 세 시스템이 만드는 반복 가능한 재미

세 시스템의 역할은 서로 다릅니다. 스스로 반복 루프를 만드는 것은 재료의 성질 하나입니다. 행동의 결합은 루프를 변형하고, 내력은 루프에 의미를 더합니다.

### 재료의 성질

반복되는 재미는 네 단계입니다. 목적을 정하고, 어디서 언제 얻을지 가설을 세우고, 다녀와서, 만든 물건을 쓰며 결과를 확인합니다.

플레이 사례입니다. 멀리까지 들리는 피리를 만들고 싶습니다. 울림은 물가 나무가 비 온 뒤에 높다는 것을 지난번에 알았습니다. 비를 기다려 개울가로 가서 나무를 살펴 고릅니다. 만든 피리를 불어 보니 소리가 마을 끝까지 닿습니다. 다음에는 단단한 도끼가 필요해 언덕으로 갑니다.

예상되는 실패와 대책입니다.

1. **정답 조합이 하나로 굳습니다.** 가장 좋은 조합이 발견되면 선택이 끝납니다. 성질끼리 맞바꿈 관계(울림이 높으면 단단함이 낮음)로 두고, 종합 품질 수치는 만들지 않습니다.
2. **차이가 숫자로만 존재합니다.** 울림 7과 9를 구별하지 못하면 시스템이 없는 것과 같습니다. 3단계로 나누고 단계마다 눈과 귀로 구분되는 차이를 둡니다.
3. **가방 정리가 일이 됩니다.** 성질이 제각각인 재료는 겹쳐 보관되지 않습니다. 단계가 같으면 겹치게 합니다. 성질 2종에 3단계면 재료당 최대 9칸입니다.
4. **다시 뽑기가 됩니다.** 성질이 무작위면 원하는 값이 나올 때까지 베는 반복이 됩니다. 장소, 날씨, 시간 규칙으로 정해지게 하면 플레이어의 지식이 성장이 됩니다.
5. **초반에 선택 근거가 없습니다.** 첫 성질은 처음부터 보이게 합니다.

### 행동의 결합

혼자서는 배치와 순서를 짜는 재미, 함께는 타이밍을 맞추는 재미입니다.

혼자 하는 사례입니다. 오르골에 자기 연주를 녹음해 큰 나무 옆에 두고 소리가 닿는 동안 벱니다. 오르골 하나로 나무 세 그루에 닿는 자리를 찾습니다.

함께 하는 사례입니다. 한 명이 피리를 불며 따라가고 다른 한 명이 나무를 고릅니다. 연주자가 곡을 바꾸면 결과가 달라져 서로 말이 오갑니다.

예상되는 실패와 대책입니다.

1. **준비 절차가 잡무가 됩니다.** 결합이 항상 이득이면 모든 행동 앞에 장치 설치가 붙습니다. 결합은 성질을 높이지 않고 바꾸게 합니다(울림은 오르고 단단함은 내림). 결합하지 않는 선택도 유효해야 합니다.
2. **한 명이 보조만 합니다.** 서서 효과만 주는 역할은 재미가 없습니다. 보조 행동도 그 자체로 놀이여야 하고(연주), 양쪽 모두 결과물을 얻어야 합니다.
3. **장치와 친구의 균형이 깨집니다.** 장치가 친구와 같으면 협동의 의미가 없고, 약하면 솔로가 손해를 봅니다. 효과의 크기는 같게, 유연성만 다르게 둡니다.
4. **조합 수가 폭증합니다.** 행동 쌍마다 효과를 따로 설계하면 감당이 안 됩니다. 행동은 소리, 빛, 향 같은 영향의 종류만 내고, 효과는 성질 축에서 한 번만 정의합니다. 질문 6에 이어집니다.

### 제작물의 내력

스스로 반복 루프를 만들지 못합니다. 기록 범위는 제작자와 핵심 재료만으로 충분하다는 의견에 동의합니다.

사례입니다. 창고에서 친구 이름이 찍힌 젖은 참나무를 발견해 악기를 만들어 두면, 악기에 두 사람의 이름이 남습니다.

예상되는 실패와 대책입니다.

1. **아무도 읽지 않는 설명문이 됩니다.** 놓인 물건에 표식을 보이게 하고, 마을 기록판에 최근 일을 적습니다.
2. **말 없는 공용 창고가 됩니다.** 의뢰 게시판을 둡니다. 친구가 필요한 것을 적으면 다른 친구의 다음 접속에 목표가 생깁니다. 개발자가 만든 콘텐츠가 바닥난 뒤에도 목표가 계속 생기는 장치는 이것뿐입니다.

### 즉각적인 재미

세 시스템 어느 것도 재검토 요청 5장의 ① 즉각적인 재미를 만들지 못합니다. 이전 의견서에 이 분석이 빠졌다는 지적은 맞습니다. 즉각적인 재미는 베는 손맛, 연주, 전투 같은 동작에서 나옵니다. 시제품에도 소리, 흔들림, 튀어나오는 재료 같은 최소한의 반응을 넣어야 판단할 수 있습니다.

## 3. 질문 2. 싱글과 협동의 차별화

도구 제한은 철회합니다. 재검토 요청이 대안으로 든 동시 행동 제한은 이전 의견서의 규칙 2와 같은 내용이라, 추가 규칙이 따로 필요합니다.

이전 의견서는 분업 압력을 목표로 잡았는데 이 설정이 틀렸다고 봅니다. 2~4인 친구 사이에 필요한 것은 서로 말을 걸 이유입니다. 그 기준으로 세 가지를 제안합니다.

1. **들고 있는 것에 따라 보이는 정보가 다릅니다.** 피리를 든 사람에게는 울림이, 등불을 든 사람에게는 광맥이 보입니다. 혼자서는 바꿔 들며 차례로 확인하고, 함께면 서로 알려 줍니다. 각자의 화면 표시만 다르면 되므로 구현 비용이 낮습니다. 혼자 할 때 바꿔 드는 일이 잦아지지 않도록 한 번 본 정보는 일정 시간 남깁니다.
2. **의뢰 게시판.** 친구가 필요한 것을 적고 다른 친구가 채웁니다. 혼자 할 때는 마을 주민이 같은 게시판에 의뢰를 올립니다. 시스템은 하나이고 의뢰의 출처만 다릅니다.
3. **자기 녹음과의 합주.** 혼자서는 오르골에 녹음한 자기 연주 위에 겹쳐 연주합니다. 함께면 실시간으로 합주합니다. 혼자 하는 쪽이 느린 판이 되지 않고 다른 놀이가 됩니다.

긴 목재를 둘이 드는 식의 물리 협동은 동기화 비용이 커서 보류를 권합니다.

## 4. 질문 3. 음악과 사냥의 비교

| 항목 | 음악 최소 시제품 | 사냥 최소 시제품 |
|---|---|---|
| 범위 | 악기 1종, 5음 건반, 8마디 녹음과 재생, 2인이 같은 박에 맞춰 연주 | 몬스터 1종, 공격 범위가 바닥에 미리 표시되는 공격 2가지, 기본 공격, 피하기, 전리품 |
| 필요한 동작 | 연주 자세 1개 | 플레이어 3~4개, 몬스터 6~8개 |
| 혼자 하는 판의 난도 | 중간 (소리의 예약 재생) | 낮음에서 중간 |
| 2인 판의 난도 | 중간 (시계 맞추기, 박 단위 정렬) | 예고형이면 중간, 반응 속도형이면 높음 |
| 즉각적인 재미 | 5음계와 박 정렬로 누구나 듣기 좋은 소리가 남. 목표가 없으면 10분 안에 소진될 수 있음 | 타격 반응(멈춤, 흔들림, 소리)에 좌우됨. 반응 없는 시제품은 실제보다 낮게 평가됨 |
| 콘텐츠 추가 비용 | 낮음. 곡은 플레이어가 만듦 | 높음. 몬스터마다 모델, 동작, 패턴이 필요 |
| 재미의 수명 | 창작이라 소진이 느림. 음악에 관심 없는 친구에게는 없음 | 패턴을 익히면 소진됨. 수치 상승 없이 늘리려면 새 몬스터가 필요 |
| 게임에 주는 것 | 표현, 공연, 남는 작품 | 위험, 장비의 쓸모, 탐험의 동기 |

최소 시제품의 비용은 비슷합니다. 차이는 그 뒤에 납니다. 사냥은 콘텐츠를 늘릴 때마다 비용이 붙고 음악은 거의 붙지 않습니다. 반면 사냥을 빼면 세계에 위험이 없고 장비 제작의 목적이 약해진다는 재검토 요청의 지적도 맞습니다.

전투 시제품에는 조건 두 가지를 붙이기를 권합니다.

1. **2인 접속 상태에서 평가합니다.** 혼자 하는 전투 판은 비용을 실제보다 작게 보여 줍니다. 비용의 대부분은 두 화면의 몬스터 상태를 맞추는 데서 나옵니다.
2. **공격을 미리 보여 주는 예고형으로 만듭니다.** 지연에 강하고, 관찰과 공략이라는 5장의 방향에 맞고, 필요한 동작 수가 적습니다.

몬스터를 소리, 빛, 향에 반응하는 개체로 정의하면 사냥이 결합 규칙 안으로 들어옵니다. 피리로 졸리게 하거나 향으로 유인한 뒤 싸우는 식입니다. 유인과 포획을 전투의 대체물로 두자던 이전 제안은 전투의 준비 단계로 옮깁니다.

## 5. 질문 4. 웹과 Godot의 비교

### 이전 의견서의 정정

Godot의 웹 내보내기는 이전 의견서가 서술한 것보다 쓸 만합니다. Godot 4.3부터 단일 스레드 내보내기가 기본이고 macOS와 iOS에서도 동작한다고 공식 문서가 적고 있습니다. 링크로 참여하는 장점을 웹 쪽에만 둔 것은 과했습니다.

### 기능별 비교

| 기능 | 웹 (TypeScript + Three.js) | Godot 4 |
|---|---|---|
| 캐릭터 이동과 동작 전환 | 중간. 전환 코드를 직접 작성 | 쉬움. 에디터에서 구성. 에디터 학습이 필요 |
| 맵 제작과 수정 | 어려움. 격자 데이터 파일과 미리보기를 직접 마련 | 쉬움. 시각 에디터 |
| 가방, 제작, 채팅 화면 | 쉬움. HTML과 CSS | 중간. 전용 UI 체계 |
| 무료 서버를 거친 2인 동기화 | 중간. 규칙 코드를 서버와 공유 | 어려움. 아래 설명 |
| 저장과 버전 변환 | 쉬움 | 쉬움 |
| 규칙 자동 테스트 | 쉬움 | 중간. 도구는 있음 |
| 음악 | 쉬움에서 중간. 소리를 정확한 시각에 예약 재생 | 중간에서 어려움. 재생이 다음 믹싱 구간에 시작되어 보정이 필요 |
| 예고형 전투 | 중간. 직접 구성 | 쉬움에서 중간. 내장 충돌 영역 |
| 브라우저 성능 | 가벼움 | WebGL 2 전용 렌더러로 제한. 실측 필요 |
| AI 수정 | 모든 것이 텍스트 코드 | 스크립트는 텍스트. 장면 연결은 에디터에서 사람이 하는 단계가 생김 |

### 가장 큰 구조적 차이

차이는 판정을 어디에 둘 수 있는가에서 납니다.

Godot의 고수준 멀티플레이 기능은 Godot으로 만든 서버를 전제로 합니다. 무료 서버리스와 연결하려면 그 기능을 쓰지 않고 메시지 규약을 직접 만들어야 합니다. 그러면 선택지가 둘입니다.

- 플레이어 한 명의 게임이 판정합니다. 4-2에서 지적하신 호스트 교체 문제를 피할 수 없습니다.
- 서버가 TypeScript로 판정하고 Godot은 화면만 그립니다. 규칙 코드가 두 언어로 나뉘고, Godot의 내장 물리와 길찾기를 서버 쪽 개체에 쓰지 못합니다.

웹은 어느 쪽이든 한 언어입니다. 상시 구동 서버에 Godot을 올리면 이 차이는 사라지지만 무료 조건과 충돌합니다. 엔진 선택은 호스트 없이 유지되는 마을이 필요한가(인계문 10장 6번), 사냥을 넣는가와 함께 정해야 합니다.

### 비교 시험

두 환경에서 같은 장면을 만들어 비교하자는 제안을 받아들입니다. 다만 작은 장면만 비교하면 Godot에 유리한 결과가 나옵니다. Godot의 장점은 첫 주에 드러나고, 웹의 장점과 Godot의 비용은 멀티플레이와 UI 단계에서 드러나기 때문입니다. 시험 항목을 이렇게 보완하기를 권합니다.

1. 동작이 있는 캐릭터가 작은 맵을 걷습니다.
2. 아이템 5종이 든 가방 화면을 엽니다.
3. 실제 무료 서버를 거쳐 두 접속자가 같은 나무를 동시에 벱니다. 한 명만 얻고, 새로고침 뒤에도 결과가 남아야 합니다.
4. AI에게 성질이 있는 새 재료를 추가하게 하고, 개발자가 손으로 해야 했던 단계를 셉니다.
5. 친구의 노트북과 휴대폰에서 링크로 열어 로딩 시간과 화면 끊김을 봅니다.

환경마다 같은 시간 상한을 두고, 판정 기준은 시작 전에 적어 둡니다. 3번과 4번에 무게를 둡니다. 이 시험은 재검토 요청 6장의 초기 기술 검증을 겸합니다.

비교 시험을 받아들이는 가장 큰 이유는 개발자 본인입니다. 에디터 작업과 코드 작업 중 어느 쪽이 덜 힘든지는 두 AI 모두 알 수 없고, 시험만이 알려 줍니다.

## 6. 기술 지적(4-2, 4-3)에 대한 답

**서버 사용량.** 요청 수 계산은 한 가지 가정에 따른 예시로 다뤄 주십시오. 실행 시간의 무료 한도는 하루 13,000GB-s로 확인했습니다. 객체 하나를 128MB로 계산하면 계정 전체에서 하루 약 28시간 분량입니다. 방이 여럿이면 이 시간을 나눠 씁니다. 무료 플랜의 호출당 CPU 한도 10ms가 서버 쪽 주기 연산에 어떻게 적용되는지는 확인하지 못했고, 기술 검증에서 실측해야 합니다.

**야생 개체.** 이전 제안을 수정합니다. 개체 연산을 서버에서 돌리면 호스트 교체 문제가 생기지 않습니다. 실행 시간은 접속해 있는 시간만큼 계산됩니다. CPU 한도에 걸릴 때의 차선책은 브라우저가 맡되 교체 때 상태를 넘기지 않고 출현 지점에서 다시 시작하는 방식입니다. 차선책에서는 전투 중 교체가 문제가 되므로, 사냥을 넣는다면 서버 실행이 사실상 전제입니다.

**합주.** 지연 문제가 없다는 표현을 정정합니다. 악보 방식에서는 각 기기가 모든 파트를 자기 시계로 재생하므로 한 사람이 듣는 파트끼리는 어긋나지 않습니다. 기기 사이에는 차이가 남습니다. 서로의 스피커 소리를 듣지 않으면 드러나지 않고, 음성 통화를 함께 쓰면 드러날 수 있습니다. 남는 문제는 세 가지입니다.

- 실시간 건반 입력을 악보 위에 얹는 경우. 입력을 다음 박에 맞춰 늦춰 재생하면 줄어듭니다.
- 블루투스 이어폰의 출력 지연.
- 곡 중간에 들어온 사람의 재생 위치.

실기기 시험이 필요하다는 의견에 동의합니다.

## 7. 질문 5. 가장 작은 시제품

| 기능 | 반드시 넣을 것 | 뺄 것 |
|---|---|---|
| 맵 | 한 화면 격자. 개울가와 언덕 | 구역 이동, 마을 |
| 채집 | 나무 2종. 성질 2종에 3단계. 장소와 비에 따른 규칙. 베기 전 살펴보기. 벨 때의 소리와 흔들림 | 채광, 약초, 숙련도 |

| 결합 | 소리가 닿는 동안 베면 성질이 바뀌는 규칙 1개 | 빛, 향 등 다른 영향 |
| 배치 | 오르골을 격자에 놓기 | 가구, 건축 |

피리가 연주의 최소 시제품을 겸합니다. 2인 판은 비교 시험의 3번 항목을 통과한 뒤 상대 표시, 공용 창고, 제작자 표식만 더합니다. 시험 중 대화는 메신저 통화로 대신합니다.

기술 검증과 게임성 검증을 나누자는 제안에 동의합니다. 두 검증은 서로 기다릴 필요가 없으므로 혼자 하는 게임성 판은 기술 검증과 병행할 수 있습니다.

관찰할 것은 네 가지입니다.

- 시키지 않아도 만들 물건에 따라 다른 나무를 고르는가. 늘 가장 가까운 나무를 벤다면 성질 시스템이 전달되지 않은 것입니다.
- 필요 없을 때에도 피리를 부는가.
- 다음 날 다시 켜는가.
- 2인 판에서 성질과 타이밍에 대해 서로 말을 하는가.

## 8. 질문 6. 확장 구조

나중에 바꾸기 어려워 처음부터 넣어야 하는 것은 다섯 가지입니다.

- 모든 상태 변경이 지나가는 명령과 이벤트 경로
- 통째로 저장할 수 있는 세계 상태
- 고정 ID
- 저장 버전과 변환 코드
- 규칙과 화면의 분리

그 위의 공통 구조는 데이터의 모양만 정해 둡니다.

1. **개체**는 종류, 성질, 반응으로 이루어집니다. 재료, 도구, 장치, 작물, 몬스터가 같은 틀을 씁니다.
2. **행동**은 필요한 도구, 대상, 걸리는 시간, 주변에 내는 영향(소리, 빛, 향, 열), 결과 규칙으로 정의합니다.
3. **결합**은 영향의 종류별로 성질을 어떻게 바꾸는지 한 번만 정의합니다.
4. **해금 조건**은 이벤트 기록에 대한 조건식으로 씁니다. 발견(처음으로 한 일)과 숙련(서로 다른 조건에서 몇 번)이 같은 형식에 담깁니다.
5. **구역**은 격자와 출현표를 담은 데이터 파일입니다.

이 틀에서 농사는 밭을 대상으로 하는 행동과 소리에 반응하는 작물이 됩니다. 낚시는 빛과 미끼에 반응하는 물고기, 요리는 향의 전달, 사냥은 영향에 반응하고 예고형 공격 데이터를 가진 개체가 됩니다.

범용 구조를 먼저 만드는 것은 권하지 않습니다. 시제품은 물건 3종을 직접 코드로 쓰고, 두 번째 스킬을 추가할 때 공통 부분을 뽑아냅니다. AI는 요청하면 범용 틀을 얼마든지 만들어 주기 때문에, 재미가 확인되기 전에 틀이 커지는 일이 쉽게 일어납니다.

## 9. 질문 7. 반대 의견

1. **장르 확장 검증 단계가 범위를 되살립니다.** 재검토 요청 6장은 음악 시제품, 사냥 시제품, 탐험 지역, 성장과 발견 시스템을 한 단계에 둡니다. 시제품은 만든 뒤에 버리기 어렵습니다. 기준 없이 실험 뒤에 범위를 정하면 애착으로 정하게 되고, 검증 단계가 재검토 요청 8장이 경계한 기능 누적의 경로가 됩니다. 실험 전에 상한과 기준을 적어 두기를 권합니다. 예를 들어 핵심 외에 공개판에 넣는 것은 음악과 사냥 중 하나로 하고, 시제품마다 시간 상한과 통과 기준을 먼저 기록합니다.
2. **정체성이 여전히 참고작의 결합으로 서술됩니다.** 재검토 요청 1장은 정체성을 세 참고작의 장점을 합친 것으로 적습니다. 인계문과 같은 문제입니다. 무엇을 하지 않는지가 들어 있어야 범위 판단의 기준으로 쓸 수 있습니다. 개발자가 정말 만들고 싶은 것이 무엇인지는 두 AI 모두 추측하고 있으므로 10장의 질문을 개발자에게 직접 물어야 합니다.
3. **숙련의 효율 향상은 인계문 4장과 충돌합니다.** 인계문은 수치 증가보다 새로운 행동을 지향한다고 적었습니다. 숙련은 조작의 변화와 선택지의 변화로 한정하기를 권합니다. 콘텐츠 소진 우려는 타당하지만 숙련 수치는 소진을 가릴 뿐입니다. 소진에 대한 답은 창작 활동(작곡, 꾸미기)과 의뢰 게시판이라고 봅니다.
4. **엔진 비교 시험의 항목이 한쪽에 유리합니다.** 5장에 적었습니다.
5. **보상 없이도 다시 하고 싶은가라는 기준을 모든 행동에 같게 적용하면 채집이 부당하게 탈락합니다.** 채집은 지루하지 않으면 충분하고 재미는 선택이 맡습니다. 연주와 전투는 그 자체로 다시 하고 싶어야 합니다.
6. **음악의 차별화에 대한 지적은 절반만 받아들입니다.** 재미가 검증되지 않았다는 점은 맞습니다. 차별화는 비슷한 것이 드문가의 문제라서 시제품 없이도 판단할 수 있습니다.

## 10. 개발자에게 물어야 할 것

두 AI의 의견이 갈리는 지점의 대부분은 이 답에 따라 정리됩니다.

- 첫 공개판에 핵심 외에 하나만 넣을 수 있다면 사냥, 음악, 꾸미기와 건축 가운데 무엇입니까?
- 함께 할 친구들은 그중 무엇을 가장 하고 싶어 합니까?
- 친구들과 접속 시간이 실제로 얼마나 겹칩니까?

## 11. 개발자 답변과 그에 따른 수정 (추가)

### 개발자의 답변

10장의 질문에 개발자가 이렇게 답했습니다.

- 가장 만들고 싶은 것은 꾸미기와 건축입니다.
- 친구들의 선호는 모릅니다. 같을 것으로 짐작하는 정도입니다.
- 친구들과 접속 시간은 거의 겹치지 않을 것으로 예상합니다.

두 답을 합치면 친구들과 함께 쓰는 마을을 각자 편한 시간에 들러 가꾸는 게임이 됩니다.

### 달라지는 결론

1. **첫 공개판의 범위.** 채집, 제작, 꾸미기와 건축, 비동기 공동 마을로 잡기를 권합니다. 9장 1번에서 제안한 상한(핵심 외에 하나)을 적용한 결과입니다. 사냥과 음악은 장기 목표에서 지운 것이 아니고 순서를 뒤로 둔 것입니다.
2. **실시간 동시 접속.** 첫 공개판에서 빼기를 권합니다. 위치 동기화, 호스트 교체, 서버 쪽 개체 연산이 필요 없어지고 4-2의 지적 대부분이 해소됩니다. 서버는 저장과 변경 순서 매김만 맡습니다. 잃는 것은 같은 화면에 함께 있는 재미입니다. 인계문 6장의 기본 요구를 바꾸는 일이라 개발자의 확답이 필요하며, 아직 받지 못했습니다.
3. **우연히 동시에 접속한 경우.** 서로의 캐릭터는 보이지 않고 변경만 반영됩니다. 창고의 같은 물건을 동시에 꺼내면 한 명만 성공해야 합니다. 이 처리는 여전히 필요합니다.
4. **엔진.** 5장에서 가장 큰 구조적 차이로 든 판정의 위치는 비동기 구조에서 대부분 사라집니다. 웹을 권한 가장 강한 근거가 약해졌습니다. 남는 비교는 웹의 UI 제작과 AI 수정 확인, Godot의 에디터와 맵 제작입니다. 무료 서버 후보도 넓어집니다. 1주 미사용 시 일시정지되는 Supabase는 여전히 맞지 않습니다.
5. **비교 시험 항목.** 5장의 3번을 바꾸고 하나를 더합니다.
   - 3번: 한 접속자가 가구를 놓고 나간 뒤 다른 접속자가 열어 봅니다. 두 접속자가 창고의 같은 물건을 동시에 꺼내면 한 명만 얻습니다.
   - 추가: 가구를 놓고, 돌리고, 옮기고, 되돌립니다.
6. **사냥.** 혼자 하는 전투가 되므로 두 화면을 맞추는 비용이 없습니다. 4장의 조건 1(2인 접속 상태에서 평가)은 필요 없어집니다. 몬스터를 늘릴 때마다 모델과 동작이 필요하다는 비용은 그대로입니다.
7. **음악.** 실시간 합주 대신, 녹음을 남기고 다른 사람이 그 위에 한 파트를 겹치는 방식이 기본이 됩니다.
8. **재료의 성질.** 겉모습 중심으로 바꿉니다. 울림과 단단함은 음악과 도구를 전제로 고른 성질이었습니다. 꾸미기가 중심이면 빛깔과 결이 먼저입니다. 같은 가구 모델에 색과 무늬만 바꾸면 모델을 더 만들지 않고 가짓수를 늘릴 수 있습니다.
9. **협동 규칙.** 제작자 표식과 의뢰 게시판은 그대로 씁니다. 3장 1번(들고 있는 것에 따라 보이는 정보가 다름)은 실시간을 전제로 하므로 보류합니다. 행동의 결합은 주변에 작용하는 가구(등불, 풍경, 오르골)의 형태로 옮기되, 뼈대의 재미가 확인된 뒤에 넣습니다.
10. **편집 권한.** 내 터는 나만 고치고 공용 광장은 모두가 고치게 합니다. 친구가 남의 배치를 실수로 바꾸는 일을 막습니다.
11. **가장 위험한 문제.** 실시간 동기화 대신 배치 조작과 3D 가구 에셋 확보가 앞에 옵니다. 이 게임에서는 배치 조작이 즉각적인 재미를 맡습니다.

| 채집 | 나무 2종. 빛깔 3단계. 장소와 비에 따른 규칙. 베기 전 살펴보기. 벨 때의 소리와 흔들림 | 채광, 약초, 숙련도 |
| 제작 | 가구 3종(의자, 탁자, 선반). 재료의 빛깔이 가구에 이어짐 | 제작법 해금, 도구 제작 |
| 배치 | 격자에 놓기, 돌리기, 옮기기, 치우기, 겹침 판정, 되돌리기 | 벽과 지붕, 층 쌓기 |
| 저장 | 로컬 저장과 버전 번호 | 서버 저장 |
| 화면 | 실제 가구 모델 3종과 색 바꾸기. 캐릭터는 캡슐 | 캐릭터 모델과 동작 |
| 그 밖 | 없음 | 연주, 주변에 작용하는 가구, 전투, 주민, 채팅, 낮밤 |

이전에는 처음 단계를 상자와 캡슐만으로 진행하자고 했습니다. 꾸미기의 재미는 눈으로 판단하므로 가구만큼은 처음부터 실제 모델을 써야 합니다. 에셋 확보라는 위험도 이때 함께 확인됩니다.

관찰할 것은 세 가지입니다.

- 원하는 색을 얻으려고 나무를 골라 찾아가는가
- 시키지 않아도 배치를 다시 바꾸는가
- 다음 날 다시 켜는가

다음 단계에서 서버 저장, 내 터와 공용 광장, 공용 창고, 제작자 표식을 더합니다. 이때는 친구가 다녀간 흔적을 보고 답례나 따라 만들기 같은 반응이 생기는지를 봅니다.

### 의견을 구하는 지점

- 실시간 동시 접속을 첫 공개판에서 빼는 데 대한 반론
- 꾸미기 중심 게임에서 성장(숙련과 발견)을 어디에 둘 것인가
- 가구 가짓수가 적은 게임의 수명을 겉모습 성질만으로 버틸 수 있는가

## 확인하지 못한 부분

- 개발자가 실시간 동시 접속 제외에 동의하는지는 아직 확인되지 않았습니다.
- 친구들의 선호와 실제 접속 시간은 개발자의 짐작이며 친구들에게 확인한 것이 아닙니다.
- 화풍이 일관된 무료 3D 가구 에셋이 충분한지는 확인하지 않았습니다. 착수 전에 먼저 살펴야 합니다.
- 겉모습 성질이 나무를 골라 찾아가는 선택을 실제로 만드는지는 시제품으로만 확인됩니다.
- Cloudflare가 객체당 128MB로 실행 시간을 계산한다는 점은 검토자의 기억입니다. 호출당 CPU 한도 10ms가 서버 쪽 주기 연산에 적용되는 방식은 확인하지 못했습니다.
- Godot의 고수준 멀티플레이 기능이 Godot 아닌 서버와 연결되지 않는다는 점은 옛 버전 공식 문서의 문구와 검색 요약에 근거합니다. 현재 버전 문서로 다시 확인해야 합니다.
- 웹 브라우저가 소리를 정확한 시각에 예약 재생한다는 점은 검토자의 기억입니다. Godot 쪽 서술은 공식 문서의 검색 요약에 근거합니다.
- 비교표의 쉬움, 중간, 어려움은 추정입니다. 비교 시험이 이 추정을 대체합니다.
- 채집과 연주, 전투에 다른 기준을 두자는 것을 포함해 게임 디자인 판단은 검토자의 의견이며 검증된 사실이 아닙니다.
- 이 세션에서는 Cloudflare 문서 사이트를 직접 열지 못해 수치는 검색 요약에 의존했습니다.
